## 一句话总结

不去“教模型识别注入”，而是用传统的系统安全手段（控制流与数据流分离、能力标签、安全策略）在模型外面构建一层防护。这样即使模型本身被注入，攻击者也无法改变 agent 的行为。在 AgentDojo 上，它首次以**可证明的安全性**完成了大部分任务。

## 背景与问题

提示注入的根本原因是：LLM 无法区分“指令”和“数据”。所有基于模型的防御（训练、提示、检测器）都可能被自适应攻击打破（见 [14](14-attacker-moves-second-usenix26.md)）。CaMeL 的问题是：能否在**不信任模型**的前提下设计出安全的 agent？

## 架构

```
用户请求（可信）
     │
     ▼
┌──────────────┐   生成 Python 风格代码（计划）
│ 特权 LLM     │ ────────────────────────────┐
│ (P-LLM)      │   只看用户请求，从不看工具输出   │
└──────────────┘                              ▼
                                     ┌──────────────────┐
                                     │ 定制解释器        │
                                     │ - 追踪数据流图     │
                                     │ - 给每个值附加能力标签│
                                     │ - 调用工具前检查策略 │
                                     └──────────────────┘
                                        │           ▲
                          不可信数据      ▼           │ 结构化结果
                                     ┌──────────────────┐
                                     │ 隔离 LLM (Q-LLM)  │
                                     │ 无工具权限，只负责把│
                                     │ 不可信数据解析成    │
                                     │ 预定义的结构       │
                                     └──────────────────┘
```

- **P-LLM**：只看可信的用户请求，生成表达计划的受限 Python 代码，**控制流在看到任何不可信数据之前就已确定**。
- **Q-LLM**：没有工具权限，只把不可信数据（邮件、网页）解析成预定义的结构；即使被注入，也只能影响数据的取值，不能改变程序结构。
- **解释器**：执行受限的 Python 子集，追踪数据流图，有 STRICT 和 NORMAL 两种模式，代码出错时最多重试 10 次。
- **能力标签**：每个值都带有元数据，记录它的来源和允许的读者。
- **安全策略**：用 Python 函数表达，在工具调用前返回允许或拒绝，被拒绝的操作需要用户确认。例如“只有当收件人来自用户输入而不是邮件内容时，才允许发邮件”。

这本质上是把操作系统和信息流控制（IFC）中的经典思想（能力机制、污点追踪）搬到了 LLM agent 上。

## 威胁模型

- 攻击者在不可信数据（邮件、文档、网页）中植入指令，试图改变数据流或工具参数；
- 假设用户的请求是可信的；
- **明确不在范围内的**：不产生数据流后果的纯文本攻击、利用注入实施的钓鱼、完全自主运行的场景。

## AgentDojo 结果

| 指标 | 未防御 | CaMeL |
|---|---|---|
| 任务完成率 | 84% | **77%**（具备可证明的安全性） |
| 成功攻击数（Gemini 2.5 Pro，共 949 次攻击） | 300 | **0** |
| 成功攻击数（Claude 3.5 Sonnet） | 次优防御（工具过滤）为 8 | **0** |

- 剩下的“成功”案例要么超出威胁模型，要么不是真正的提示注入。
- Travel 环境是主要短板，原因是工具输出的文档质量差。
- **开销**：中位任务的输入 token 约为原生工具调用的 2.82 倍，输出 token 约为 2.73 倍。

## 局限（作者自述）

- **侧信道**：攻击者可能通过间接的工具调用、异常导致的单比特泄露或时序推断出隐私数据。
- **策略负担**：需要用户或开发者定义并维护安全策略。
- **用户疲劳**：频繁的确认请求可能导致用户随手批准恶意操作。
- **生态依赖**：完整的保护需要工具支持能力标签，第三方服务难以做到。
- 可能存在类似 ROP 的攻击（把允许的控制流串起来实现恶意目的）；解释器很复杂，尚未经过形式化验证。

## 贡献与意义

1. **范式转变**：从“让模型更鲁棒”转向“让系统在模型不可靠的情况下仍然安全”，这也是对 [14](14-attacker-moves-second-usenix26.md) 结论的正面回应。
2. 首次在标准基准上实现**有安全保证**的提示注入防御，而不仅仅是“经验上难以攻破”。
3. 把经典系统安全（能力、信息流控制）引入 LLM agent，打通了两个研究社区。

## 对研究者的启示

- 策略的自动生成和验证、侧信道分析、形式化验证解释器，都是直接的后续研究方向。
- “双 LLM 模式”（Simon Willison 2023 年提出）加上能力标签的设计，可以推广到 MCP 等 agent 工具协议。
